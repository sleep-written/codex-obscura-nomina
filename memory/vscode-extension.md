`./vscode-extension` da soporte de editor a `.lyrics` en VSCode, construido sobre [[lyrics-ast]] (`parseLyrics`/`locate`), [[lyrics-printer]] (`printLyrics`) y [[lyrics-phonetics]] (`parsePlainLyrics`): IntelliSense (hover/outline/completion), diagnósticos, formatting, comandos de escritura (anotar/toggle), syntax highlighting (gramática TextMate), y auto-inyección de colores por defecto. Agregado como carpeta al `.code-workspace` raíz.

**De solo lectura a lectura+escritura:** la extensión se creó (`7a30ff9`) cuando `lyrics-language` solo exponía `parseLyrics`/`locate` — todo lo que hacía era mostrar información (hover/outline/completion heurístico). Cuando el paquete ganó `parsePlainLyrics`/`printLyrics`/`printPlainLyrics` (ver [[lyrics-phonetics]]/[[lyrics-printer]]), la extensión no los consumía. Se cerró ese desfase agregando una capa de escritura: diagnósticos, `DocumentFormattingEditProvider`, y comandos que editan el documento. **Deliberadamente no se agregó** ningún comando de `printPlainLyrics` (exportar a texto plano) — fuera del alcance pedido por el usuario.

**Decisión explícita: NO se exporta la fonética (`spanish-vowels.ts`) al lado de la extensión.** El README de `lyrics-language` declara ese módulo deliberadamente no-público (ver [[lyrics-phonetics]]). `providers/completion-context.ts` sigue con su propia lista local de vocales y sin decidir cuál símbolo de un par alterable es "correcto" — misma regla que ya aplicaba antes de este cambio, extendida ahora también a `src/markers.ts` (toggle de alteraciones: solo invierte/permuta el símbolo, nunca evalúa fonética).

**Arquitectura elegida — API directa de VSCode, no LSP:** un solo paquete de extensión que llama `parseLyrics()`/`locate()` en el extension host y registra `vscode.languages.register*Provider` directamente. Se descartó un Language Server (`vscode-languageserver`/`vscode-languageclient`) porque no hay necesidad de portabilidad a otros editores todavía — menos piezas (sin proceso separado, sin sincronización de documentos vía LSP).

**Estructura:**
- `document-store.ts` — `getParsed(document)`, cache pull-based por `document.version`; captura solo `LyricsParseError` (cualquier otro error se relanza, no se silencia un bug propio). Reusado también por `diagnostics.ts` y `commands/toggle-marker.ts` — un solo parse por versión de documento sirve a todo.
- `position.ts` — conversión `vscode.Position` (0-idx) ↔ `Position` de lyrics-language (1-idx); `toVscodeRange`.
- `markers.ts` (+ `markers.test.ts`) — puro, sin `import 'vscode'`. `toggleSymbol(marker)` invierte `active` manteniendo `kind` (`+`↔`_`, `%`↔`/`, `&`↔espacio). `describeMarkerState(kind, active)` (movido aquí desde `providers/hover.ts`, era `MARKER_DESCRIPTIONS` local) es el texto descriptivo por combinación, reusado tanto para el estado actual como para el destino del toggle en el hover. **Deliberadamente no ofrece cambiar de `kind`** (ej. `_` → `%`): una versión inicial sí lo hacía (`switchKindSymbol`, preservando el efecto métrico entre diéresis/sinéresis) y el usuario lo corrigió — diéresis y sinéresis son fenómenos distintos del DSL, y sugerir uno desde el hover del otro se lee como que la herramienta los confunde. Se eliminó por completo (función, comando `lyrics.switchMarkerKind`, entrada en `package.json`), no solo se ocultó.
- `diagnostics.ts` — `registerDiagnostics(context)`: un `DiagnosticCollection` poblado desde `getParsed(document).error` en open/change, `collection.delete` en close. `LyricsParseError` solo trae un punto `line`/`column` (no rango) — se expande hasta fin de línea, o la línea completa si el punto ya está al final; `line` se clampea contra `document.lineCount` (un error de fin de archivo puede apuntar una línea de más). Reemplazó la rama "Parse error" que antes vivía en `providers/hover.ts` (solo visible con el cursor exacto sobre la columna del error) — ahora `hover.ts` devuelve `undefined` si `song === null` y confía en el squiggle.
- `commands/toggle-marker.ts` — `resolveMarkerAt(document, position)`: re-localiza el `AlterableMarker` bajo una posición vía `getParsed`+`locate` (nunca confía en un nodo pasado por el llamador, para no actuar sobre AST desactualizado). Registra `lyrics.toggleMarker`, acepta un argumento opcional `{ line, character }` (0-idx); sin argumento usa el cursor del editor activo. Consumido por dos superficies: el link `command:` del hover (`providers/hover.ts`, requiere `MarkdownString.isTrusted = true`) y `providers/code-actions.ts` (`Ctrl+.`/lightbulb, `CodeActionKind.RefactorRewrite`, edita vía `WorkspaceEdit` directo sin pasar por el comando).
- `commands/annotate.ts` — `lyrics.annotate`: `parsePlainLyrics` + `printLyrics` sobre la selección (o todo el documento si no hay selección). Guardia **exacta** (no heurística de caracteres) contra destruir anotación manual: intenta `parseLyrics(source)` primero; si tiene éxito, pide confirmación modal antes de re-anotar (perdería cualquier `+`/`%` puesto a mano — `parsePlainLyrics` descarta todo símbolo DSL suelto, ver [[lyrics-phonetics]]). Si el rango no terminaba en `\n`, se recorta el `\n` final que `printLyrics` siempre agrega, para no inyectar una línea al anotar una selección a mitad de archivo.
- `providers/formatting.ts` — `LyricsDocumentFormattingEditProvider`: `printLyrics(getParsed(document).song)` reemplaza todo el documento (`Shift+Alt+F`); `[]` si el parse falló (diagnostics ya explica por qué) o si el resultado es idéntico al texto actual (no ensucia el undo stack).
- `providers/hover.ts`, `providers/document-symbols.ts` (outline con breadcrumbs canción→estrofa→verso, usa `title.range` como `selectionRange`), `providers/completion.ts` + `providers/completion-context.ts`, `providers/code-actions.ts`.
- `token-colors.ts` + `activation.ts` — ver sección de colores abajo.
- `syntaxes/lyrics.tmLanguage.json` — gramática TextMate, scopes por símbolo del DSL (ver [[lyrics-language-dsl]] para la tabla): `markup.heading.1/2.lyrics` (títulos), `comment.line.double-slash.lyrics`, `punctuation.separator.syllable.lyrics` (`-`), `keyword.operator.{sinalefa-on,sinalefa-off,diaeresis-on,diaeresis-off,synaeresis-on,synaeresis-off}.lyrics`. El patrón de comentario (`//`) va ANTES del de `synaeresis-off` (`/`) en el array `patterns` para ganar el empate de posición inicial, igual que `CommentFactory` en el tokenizer (ver [[lyrics-tokenizer]]).
- `package.json#contributes` — `commands` (`lyrics.annotate`/`lyrics.toggleMarker`, categoría "Lyrics"), `menus.commandPalette`/`editor/context` con `"when": "editorLangId == lyrics"`, `keybindings` (`alt+t` → `lyrics.toggleMarker`).

**Completion es heurística de texto crudo, no del AST:** mientras se escribe, el documento suele estar momentáneamente inválido para `parseLyrics` (ej. un `#` suelto), así que `completion-context.ts` (sin `import 'vscode'`, testeable con `node --test`) mira los caracteres antes/después del cursor directamente. Nunca decide cuál símbolo de un par alterable es "correcto" (no hay motor de fonética) — siempre ofrece las 4 opciones (`+`/`_`/`%`/`/`) juntas cuando el cursor está entre dos vocales.

**Build: esbuild, no `@bleed-believer/cli`.** `lyrics-language` solo declara la condición `"import"` en su `package.json` (ESM puro, sin `"require"`) — un build con `bleed build` (que solo transpila 1:1 vía `tsc`, no bundlea) dejaría un `require('@codex-obscura-nomina/lyrics-language')` real en el `.cjs` final, que revienta con `ERR_PACKAGE_PATH_NOT_EXPORTED` (confirmado directamente). esbuild resuelve esto bundleando/inlineando el código fuente al momento de build, sin depender de resolución en runtime. Además el extension host de VSCode espera un `main` CommonJS (o bundle presentado como tal) — por eso tampoco sirve compilar a ESM puro.

**Dos gotchas de build ya resueltos, no repetirlos:**
1. esbuild hace *upward directory search* del `tsconfig.json` más cercano **por cada archivo bundleado**, no solo el entry point. Como `lyrics-language/dist/index.js` no tiene tsconfig en su propia carpeta, esbuild subía hasta `lyrics-language/tsconfig.json` y tropezaba con `target: "es2025"` (no reconocido por esbuild) → warning. Fix: pinear `tsconfig: 'tsconfig.json'` explícito en `esbuild.config.mjs`, evita el upward-walk por completo.
2. `package.json` tiene `"type": "module"` (necesario para que `@bleed-believer/cli` corra los `*.test.ts` como ESM), pero el bundle de esbuild es CommonJS (`format: 'cjs'`). Con `"type": "module"`, Node trata cualquier `.js` como ESM sin importar el contenido → `"module is not defined in ES module scope"` al activar la extensión. Fix: el bundle se emite como `dist/extension.cjs` (no `.js`) — la extensión `.cjs` fuerza CommonJS en Node pase lo que diga `package.json`. `main` y `launch.json`'s `outFiles` actualizados a juego.

**Colores por defecto — por qué la extensión los inyecta en settings, no solo la gramática:** una gramática TextMate solo asigna *scopes*; el color siempre lo decide el tema activo. Muchos temas simplemente no cubren categorías genéricas — confirmado leyendo directamente el `.tmTheme` del tema del usuario ("Evil Red Theme"): tiene reglas para `comment`/`keyword`/`string`/etc. pero **ninguna para `punctuation`**, así que cualquier scope `punctuation.*` cae al foreground default sin importar el nombre exacto que se le ponga. No hay forma de que una extensión de lenguaje fuerce un color en el tema de otro sin: (a) traer su propio tema completo (`contributes.themes`, pero el usuario dejaría de ver su tema mientras edita `.lyrics`), o (b) escribir a `editor.tokenColorCustomizations` del usuario. Se implementó (b): `token-colors.ts` (puro, testeable — `LYRICS_TOKEN_COLOR_RULES` + `mergeTokenColorRules`, que solo agrega scopes que el usuario no haya cubierto ya, preservando cualquier color propio) y `activation.ts` (`ensureTokenColors`, usa `vscode.workspace.getConfiguration().update(..., ConfigurationTarget.Global)`), llamado en `extension.ts#activate`. Colores actuales: gris oscuro `#5c5c5c` para separador de sílaba, verde `#4caf50` para alteraciones activadas (`&`/`+`/`%`), azul `#4a9eff` para desactivadas (`_`/`/`).

**Why:** mutar `editor.tokenColorCustomizations` global desde una extensión no es el patrón recomendado para extensiones de marketplace (puede pisar a otras extensiones, persiste tras desinstalar) — se decidió igual porque esta es una herramienta personal de un solo usuario para su propio DSL, no algo a publicar.

**How to apply:** cualquier símbolo nuevo del DSL necesita: entrada en `lyrics.tmLanguage.json` (scope nuevo), regla de color en `LYRICS_TOKEN_COLOR_RULES` si aplica, y actualizar `describeMarkerState`/`toggleSymbol` en `markers.ts` (no `providers/hover.ts`, que ahora solo consume `markers.ts`). No agregar de vuelta un cruce diéresis↔sinéresis sin confirmarlo explícitamente con el usuario — ver el punto arriba. Ver [[gotcha-agent-sandbox-home]] (memoria global) antes de intentar depurar o editar configuración de VSCode del usuario por fuera de la extensión misma — el shell de este agente NO comparte `$HOME` con la sesión real de VSCode del usuario, aunque los paths del proyecto se vean idénticos.
